SHORT VERSION
  - The network does not work, and we now know it for sure (774 epochs).
  - A single fixed 3-number correction does the same job as the network.
  - BUT that "constant" is not really a constant -- it changes with the time

  - Net result you can ship: use it for LONG outages (2 min), do NOT use it
    for short ones (30-60 s). At short horizons the 15 s freeze alone is
    already as good as anything we have.

2. THE CONTROL TEST: 3 NUMBERS BEAT THE NETWORK
-------------------------------------------------------------------------------
  New tool: tools/const_bias_control.py
  It fits ONE fixed 3-number correction on the training flights, with NO
  network at all, and scores it on the held-out flights the same way.

  On held-out flights (lower is better):

      cell        3 numbers    the network (138,802 weights)   winner
      30 s pos      1.0015              1.0034                 3 numbers
      60 s pos      0.9991              0.9974                 network
      120 s pos     0.9683              0.9699                 3 numbers

  The 3 numbers win 4 of 6 cells. The biggest gap anywhere is 0.0026, while
  the flight-to-flight spread is 0.03-0.05 -- so they are the same thing.
  The network even LOSES on its own selection data (0.9894 vs 0.9786).

  Why: the network's average output points the same direction as the fitted
  constant (cosine 0.97) at half the size. It spent 138,802 weights learning
  a worse version of 3 numbers.

-------------------------------------------------------------------------------
3. THE CATCH: THE "CONSTANT" IS NOT CONSTANT
-------------------------------------------------------------------------------
  I fitted it separately at each horizon. A real sensor bias would come out
  the same every time. It does not:

      fitted at      the 3 numbers (m/s^2)              size
        30 s      [+0.0034, +0.0088, +0.0078]          0.0123
        60 s      [+0.0081, +0.0130, +0.0060]          0.0165
       120 s      [+0.0192, +0.0118, +0.0044]          0.0229

  The size nearly DOUBLES from the 30 s fit to the 120 s fit, and the first
  number grows 5.6x while the third one shrinks.

  What that means: it is not measuring a sensor bias. It is soaking up
  ATTITUDE error. A small tilt error leaks gravity into the horizontal
  direction, and that error grows faster than a straight line -- so the fit
  needs a bigger number the longer the window. Do not call it "the bias".

  This also re-explains section 2: the network was not failing to learn a
  bias. THERE WAS NO CONSTANT BIAS TO LEARN. Both arms were fitting attitude
  leakage, and the network just did it worse.

  wants its own number is itself the proof it is not a constant.

5. FIXES I MADE (so future numbers can be trusted)
-------------------------------------------------------------------------------
  1. ADDED A RANDOM SEED  <-- the important one
     train.py never set one. Every run started from different random weights
     and shuffled differently, so every config comparison we ever made was
     also comparing two random draws -- and the differences we cared about
     (1-2%) were smaller than that random spread.
     Now: --seed (default 0), recorded into parameters.yaml.

  2. FIXED A WRONG AVERAGE IN THE VALIDATION SCORE
     It averaged each BATCH equally. With 101 windows at batch 64 you get
     batches of 64 and 37, so the last 37 windows counted for half the score
     instead of a third. Your 60 s number moves 123.76 m -> 121.47 m.
     Nothing got worse; the old number was measured wrong. NOTE: new runs
     are not directly comparable to old ones.

  3. FIXED A HOLE THAT SKIPPED THE DATA QUALITY CHECK
     "evaluate" mode built windows WITHOUT the check that rejects windows
     containing recording gaps -- so the held-out test used windows training
     would never have accepted, including one spanning a 0.14 s gap. Both
     use the same rule now. (Re-ran the held-out result: conclusion unchanged.)

  4. eval.py NO LONGER INVENTS RESULTS
     A wrong checkpoint path printed "no model loaded" and then printed a
     full, normal-looking table -- from RANDOM weights. Now it stops.

  5. NEW: --per_flight ON THE EVALUATION TOOL
     One pooled number hides too much. All in one view now:
         pooled          1.003   (looks like nothing happened)
         typical flight  0.967   (3% better)
         one flight      1.027   and it carries 53% of the total error
     One bad flight was deciding the verdict.

  6. Small: corrected a wrong label ("raw, uncorrected IMU" -- it already has
     the 15 s freeze applied), and added a missing setting so hybrid_best can
     be tested on the held-out flights at all.
