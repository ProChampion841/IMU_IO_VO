What changed, one line each. Newest section first.


1. FLOW MEASUREMENT (ACCURACY)
------------------------------
1.1  Two problems both made the measured ground motion too small, and speed comes from that motion.
1.2  Problem A: the grid squares were averaged plainly, mixing good measurements with squares that saw nothing.
1.3  A square that cannot match gives the answer zero, so the average was pulled down toward zero.
1.4  How far down depended on the ground, so the error changed while flying and could not be learned away.
1.5  Fix A: weight each square by the confidence the model already computes, instead of a plain average.
1.6  A later layer could NOT have fixed this: two very different scenes can give identical averages.
1.7  Problem B: the answer was averaged over all 81 candidate movements, including the very unlikely ones.
1.8  Those far candidates dragged the answer toward the middle, so motion was under-reported by about 3x.
1.9  Fix B: pick the best candidate first, then average only its 8 neighbours for the fine detail.
1.10 Measured together on a known 2-cell shift: error fell 90% with 40% of the ground untrackable.
1.11 With clean ground the answer is now exact (2.000) where it used to read 1.943.
1.12 The two fixes depend on each other: B alone makes a blank square report confident nonsense, and A hides it.
1.13 A new weight channel says "nothing was measured here", which is not the same as "the motion was zero".
1.14 Cell channels went 7 to 9, so the model is 684,975 params, 1.7% larger, and old checkpoints will not load.
1.15 The old shrinking behaviour is still under test, so nobody reintroduces it by accident.
1.16 Review follow-up: a square with NO information was still being counted as measured.
1.17 A tie between all 81 candidates still scores 1/81, so the confidence never reached zero.
1.18 When a whole region was blank the weighting cancelled out and it reported a big wrong number (-3.0).
1.19 Fix: subtract the no-information floor first, so a blank region now gets weight exactly zero.
1.20 Fix: at the edge of the search the window is now cut short instead of slid inward, which biased it.
1.21 The blank-region test no longer hides behind an "if", so it cannot pass by never running.
1.22 The search size is unchanged at 81 candidates: making it smaller is a speed win, not an accuracy one.
1.23 Review follow-up 2: the maths changed but the version name did not, so old weights still loaded.
1.24 Same tensor shapes, different meaning, and a strict load cannot see the difference.
1.25 The frontend is now v3, and the name is written into both the checkpoint and the resume check.
1.26 A checkpoint with no version, or an older one, is now refused by name instead of loaded quietly.
1.27 Checked end to end: a v3 checkpoint relabelled v2 is still refused, so the name is doing the work.


2. TIME ALIGNMENT
-----------------
2.1  Altitude and attitude are now read at the exact photo time, not at the nearest row.
2.2  Rotation is averaged over the real shutter window instead of taken from one sample.
2.3  The time between two photos comes from their file names, never from a fixed frame rate.
2.4  Photos taken during a telemetry gap are dropped, because a guess across a hole is not a measurement.
2.5  A gap counts as a hole when it is 8x longer than normal, so normal jitter is safe.
2.6  --max-frame-gap-s drops a photo pair when the camera missed frames between them.
2.7  --image-time-offset fixes a camera clock that is early, late, or drifting. Off by default.
2.8  A fixed clock offset cannot be seen in the timestamps alone; use tools/estimate_time_offset.py.

11. ROTATION IS NOW REMOVED PER CELL, AND A CORRELATOR BUG IS FIXED
--------------------------------------------------------------------
11.1  Turning an aircraft moves the image differently in different places.
11.2  The old code predicted ONE shift for the whole picture and subtracted that.
11.3  For the part of the turn that spins the picture about its centre, that can
      never work: the spin pushes one side one way and the other side the other,
      so the best single number is exactly zero and nothing at all is removed.
11.4  Measured in the new test: a constant removes 0% of that spin, and 96-97%
      of the other two rotation directions. So one axis was completely uncorrected.
11.5  The fix evaluates the real rotation pattern at every cell. The correlator
      already accepted a per-cell input; nothing had ever supplied one.
11.6  The camera mounting is still not needed. A learned 3x3 map covers every
      possible mounting, so the geometry is fixed and the orientation is learned.
11.7  It still starts at zero, so the search begins centred and earns every offset.
11.8  Measured end to end on a known spin, error in the recovered sideways motion:
      spin 1.5 cells, 50% better; spin 3 cells, 66% better.
11.9  HONEST LIMIT: at the spin size this aircraft actually produces, about 0.4
      to 0.8 cells, the gain is between break-even and 16%. It only pays off
      properly once the picture resolution is raised.
11.10 SEPARATE BUG FOUND, AND IT IS THE BIGGER ONE. The correlator lost up to
      HALF the measured motion whenever the predicted shift was not a whole cell.
11.11 On a known 2-cell shift: whole-number shifts gave 2.00 every time, but
      half-cell shifts gave 1.00 to 1.66. It survived every texture tested.
11.12 The old code fed it a learned shift that is almost never a whole number,
      and its size grows with turn rate, so the loss grew during turns.
11.13 That is a turn-correlated shrinking of measured motion, which is exactly
      the error shape this frontend cannot absorb, aimed at the worst axis.
11.14 Fix: the search is rounded to whole cells. Nothing is lost, because all
      the fine detail comes from the sub-cell step, which is exact on whole cells.
11.15 Rounding passes the gradient straight through, or the map could never learn.
11.16 The reported motion now subtracts the EXACT rotation, not the rounded one,
      so the rounding cannot leak back in as fake sideways motion.
11.17 --rotation-mode field or constant, so the change can be tested, not assumed.
11.18 The frontend is now v4 and the mode is in the fingerprint, so old weights
      are refused by name rather than loaded into different maths.
11.19 Whole suite green: 195 tests.

13. RUNBOOK AND EVALUATION FIXES, FOUND BY EXTERNAL REVIEW OF THE v4 CHANGE
------------------------------------------------------------------------------
13.1  BIGGEST ONE: the frontend was handed the camera matrix at NATIVE
      (calibration) resolution, in both the trainer and the evaluator.
13.2  But the frontend only ever sees images already resized to the WORKING
      resolution, and it infers "native size" from the image tensor it is
      actually given - so its own native/working rescale was silently a
      no-op, and the raw native fx/fy/cx/cy were used as if already at
      working scale.
13.3  At a typical 1920x1080 native / 576x1024 working size that overstates
      focal length by about 1.875x and misplaces the principal point by
      hundreds of working pixels.
13.4  This corrupted both the bearing scale AND the new per-cell rotational
      field's coordinate grid - so every v4 number to date needs a retrain to
      be trusted, not just re-reading.
13.5  Fix: resize the matrix once, with the same helper VisualPairSource
      already trusts, before it reaches the frontend.
13.6  Lens distortion was parsed from the calibration file and then dropped:
      build_vo_dataset() had no parameter to carry it to VisualPairSource, so
      a calibration with real distortion had it silently ignored by every
      caller. Wired through, and added to the resume fingerprint.
13.7  The evaluator always built a "field" frontend regardless of what a
      checkpoint actually recorded, so scoring a "constant" checkpoint could
      load the wrong-shaped weights or silently score under the wrong
      geometry. Now restores rotation_mode from the checkpoint, defaulting to
      "constant" only when the key predates the field mode existing at all -
      the same convention the trainer's own resume check already used.
13.8  A missing raw log altitude used to fall back to the CENTRED copy in the
      aiding vector, which would have scaled every predicted speed by a
      constant nobody would think to look for. Now refuses instead of
      guessing.
13.9  Added a cold-start warm-up diagnostic: every horizon leg starts from a
      zeroed state, so no visual event can exist before one deployment
      latency plus about one camera frame interval have elapsed, and a
      shorter --warmup silently scores those ticks as live. Diagnostic only -
      the right cold-start warmup is still an open question.
13.10 PRE-SPLIT evaluation bug: _resolve_ranges maps every phase to the WHOLE
      scored directory, so the evaluator's "train mean" baseline was actually
      the mean of whichever folder was being scored - comparing a model
      against its own validation (or test) mean, flattering every
      skill/baseline number. The true training mean is now recorded in the
      checkpoint at training time and read from there; an older checkpoint
      falls back to recomputing it from the recorded training folder, never
      from the folder being scored.
13.11 PRE-SPLIT training bug, latent until --horizon-minutes is used with a
      pre-split run: the optional in-training horizon pass always read
      datasets["train"] and the training file's own clock, regardless of
      --horizon-split. Harmless when every phase shares one file (the
      fractional-split mode this was written for) but in a pre-split run each
      phase is a different directory, so a "validation" horizon leg would
      have silently scored a slice of the TRAINING file under the validation
      label. Now reads datasets[args.horizon_split] and that dataset's own
      attitude.
13.12 commands.txt: the resume command had dropped --test-dataset, which
      changes the fingerprinted split ranges and would have been refused by
      name; the "spelled out" torchrun command had dropped --save-every and
      --keep-last; the test-split evaluation command never passed --splits
      test, so its JSON labelled a test-set result as validation; only one of
      three seeds was listed per rotation-mode arm. All four fixed.
13.13 Doc cleanup: the frontend_id version-history comment now has a "v4:"
      entry (it only had v2/v3); correlation.py no longer calls the search
      centre a "gyro/IMU prediction" (this project has no gyro); the
      --rotation-map error messages no longer point at
      tools/calibrate_camera_imu_rotation.py as if it exists - it does not
      ship in this repository, and the messages now say so and give the
      expected JSON shape instead.
13.14 Whole suite green: 201 tests.

15. INCREMENT 2 OF THE POST-BUGFIX ROADMAP: AIDING-VECTOR ADDITIONS
--------------------------------------------------------------------------
15.1  The aiding vector carried sin/cos roll, sin/cos pitch and log altitude
      but no body rate at all - a coordinated turn holds roll and pitch near
      constant while yaw rate carries the whole manoeuvre, invisible to those
      four channels.
15.2  Fixed: aiding_features (vio/data/attitude.py) appends p, q, r - the
      SAME body_rate_rad_s the loader already derives at load time
      (Log(R_{i-1}^T R_i) / dt), not a fresh differentiation. VO_AIDING_CHANNELS
      and AIDING_INPUT_DIM (6 -> 9) grew to match; log altitude stayed at
      index 4, so nothing already reading that index moved.
15.3  Fusion input gained a second scalar alongside visual_present:
      visual_age, ticks since the last delivered visual token
      (vio.data.fixedwing_vo.visual_age_ticks). visual_present alone conflates
      "no image yet" with "the image showed zero motion"; visual_age lets the
      encoder discount a held-over token by its own staleness from the first
      gradient step instead of having to infer it from recurrence alone.
15.4  visual_age_ticks is causal and call-local: zero on the tick a token
      arrives, growing by one every tick after, and counting from the call's
      own start (not "unknown") before the first token that call can see -
      the same boundary scatter_visual_tokens already draws for
      visual_present itself.
15.5  The streamed evaluator (run_span_horizons) computes visual_age_ticks
      ONCE over the whole span and slices it per block, exactly like
      token_field/quality_field/present_field, so age stays continuous across
      a block boundary; a genuine state reset instead computes it fresh on
      the reset slice, which is what makes it forget staleness along with
      everything else.
15.6  fuse_stream/fuse/forward/forward_stream all gained a required
      visual_age positional argument (no silent default): AIDING_INPUT_DIM
      is a hard-coded constant, not a CLI flag, so a resume against a
      pre-Increment-2 checkpoint already fails loudly at the trainer's and
      evaluator's load_state_dict(strict=True) rather than silently
      continuing under the old channel count.
15.7  New integration test trains on a flight with a known constant yaw rate
      (0.02 rad/s) and confirms, via a spy on VisionMambaVO.forward, that:
      the captured aiding vector's r channel sits at that rate and p/q sit at
      zero; visual_age is exactly zero wherever visual_present fires; and
      visual_age exceeds the camera's own nominal frame-to-frame gap. Reverting
      the visual_age wiring in VOStep.forward was checked to fail this test
      before landing the fix.
15.8  Shared-frame re-encoding dedup remains its own, not-yet-started
      increment (see the approved plan) - deliberately skipped again here.
15.9  Whole suite green: 210 tests.


16. INCREMENT 3 OF THE POST-BUGFIX ROADMAP: TBPTT DESIGN + LOCAL SCAFFOLD
--------------------------------------------------------------------------
16.1  Design note first, as planned (PLAN_TBPTT.txt): the roadmap's own "low
      risk" label for TBPTT did not survive checking three things against
      the actual code - windows overlap 50% by default, the training
      DistributedSampler always shuffles, and CausalMambaEncoder.detach_state
      had zero call sites anywhere in the repository. All three are load-
      bearing design constraints, not implementation details.
16.2  New ChronologicalWindowSampler (vio/data/fixedwing_vo.py): splits a
      dataset's own window order into batch_size independent lanes, each
      walking forward in time, and records per lane per step whether that
      step is the TRUE chronological successor of the lane's previous one -
      false at step 0 always, and also whenever a lane's walk crosses an
      index_ranges boundary, since a condition-segment split assigns
      disjoint spans to one phase and two of them being in tick order does
      not mean they were flown back to back.
16.3  Requires stride == window_length, checked against the realized
      dataset.starts tiling rather than a stored stride (the dataset does
      not keep one). Refuses construction otherwise: an overlapping window
      would either be double-processed or need a tick-level re-seen mask
      this scaffold does not implement.
16.4  New mask_stream_state / detach_stream_state (vision_mamba_vo.py).
      Masking a lane to zero and carrying a lane forward are the SAME
      operation (multiply by a 0/1 keep mask) because a block's
      initial_state is already all zeros - not two code paths that happen
      to agree. Detaching finally gives CausalMambaEncoder.detach_state its
      first real caller.
16.5  VOStep gained forward_stream (tools/train_fixedwing_vo.py), sharing a
      new _encode_visual helper with the existing forward - a pure refactor,
      confirmed by the full suite passing unchanged before and after. New
      forward_batch_stream mirrors forward_batch, threading VOStreamState in
      and out. Both are explicitly NOT DDP-safe: DistributedDataParallel's
      gradient-sync hooks fire on the wrapped module's own forward(), and a
      differently-named method bypasses them silently - documented as
      deferred, not worked around.
16.6  Nothing wired into the CLI. This increment ships tested primitives,
      not a new --tbptt training mode: the epoch-loop wiring needs its own
      decisions (metrics.csv columns, validation semantics, --eval-train-
      split interaction) better made in a dedicated follow-up once these are
      reviewed. See PLAN_TBPTT.txt section 7 for the full deferred list -
      DDP per-rank-lane threading and mid-sequence checkpoint resume chief
      among them.
16.7  New integration test runs the REAL frontend/dataset/VOStep/sampler
      pipeline for two TBPTT steps: carrying state into step 1 changes its
      prediction relative to a state=None run of the same batch, and
      detaching the carried state changes nothing about step 1's own forward
      values. Reverting forward_batch_stream's state threading was checked
      to fail this test before landing the fix.
16.8  Whole suite green: 217 tests.


17. INCREMENT 3.1 HARDENING PASS, PER CODEX'S THIRD REVIEW
--------------------------------------------------------------------------
Codex re-reviewed increments 2 and 3, independently reran a subset of the
suite (8 tests, all passing), and found the WORK sound but not yet ready for
server training or TBPTT activation: several semantic and GPU-specific gaps.
This section is that hardening pass and nothing else - no CLI wiring for
TBPTT, no new architecture, exactly as the review asked.

17.1  visual_age was not physical age. visual_age_ticks reported 0 the tick
      a token arrived, but that tick is ready_tick - one deployment latency
      (0.35s default) AFTER the second image was actually captured (see
      VisualPairSource) - so the image was already ~0.35-0.39s old at the
      moment it became "fresh" in the old accounting. It also counted ticks,
      not seconds, so an irregular telemetry clock (a dropped sample) was
      measured wrong.
17.2  Fixed: visual_age_ticks -> visual_age_seconds(present, times_s,
      deployment_latency_s, carry=None). age(t) = (times_s[t] -
      times_s[last_delivery_tick]) + deployment_latency_s for any tick at or
      after a delivery this call can see; exactly 0 before the first
      delivery (or when present is all zero, e.g. --disable-visual-input)
      because there is no captured image yet to be stale. Uses the REAL
      clock throughout, not an assumed uniform interval.
17.3  Continuity across a TBPTT chunk boundary needed a NEW piece of carried
      state - the age-side counterpart of VOStreamState - since a window

18. VALIDATION FRONTEND-CHUNK BYPASS (MEMORY REGRESSION, CODEX'S 4TH REVIEW)
-----------------------------------------------------------------------------
18.1  Real bug, found from an actual Ubuntu multi-GPU crash report, not a
      local repro: tools/train_fixedwing_vo.py's encode_pairs() read
      `if chunk <= 0 or not torch.is_grad_enabled(): ... one call with every
      pair`. evaluate() and run_horizon_pass() both run under
      torch.no_grad(), so EVERY validation pass silently ignored
      --frontend-chunk and sent the whole batch's pairs through the frontend
      - and its correlator - in one call. Confirmed against the actual code
      (tools/train_fixedwing_vo.py, src/vio/models/correlation.py) before
      changing anything, same discipline as every other fix this session.
18.2  Why it only became fatal recently: the correlator used to loop over
      its ~81 search candidates one at a time (a Python loop of per-offset
      grid_sample calls). Increment 1's vectorisation (src/vio/models/
      correlation.py's _all_integer_shifts/_all_grid_samples) replaced that
      loop with one call building a (pairs, channels, candidates, height,
      width) tensor - faster for a bounded chunk, but the validation bypass
      above meant "pairs" was the WHOLE batch, not the chunk. At the
      trainer's real defaults (batch 4, 120 events/window, 64 channels, 81
      candidates, 72x128 grid) that is 480 pairs and ~85.4 GiB for a single
      tensor - on top of images, feature maps, sampling grids, logits,
      softmax probabilities and the fusion state. Ten 80 GiB GPUs do not
      pool into 800 GiB; each DDP rank needs this to fit alone.
18.3  Fix, in tools/train_fixedwing_vo.py's encode_pairs(): chunk whenever
      chunk > 0, REGARDLESS of grad state. Only the checkpoint()
      recompute-in-backward wrapper is conditioned on
      torch.is_grad_enabled() now - under no_grad there is nothing to
      recompute for, so each chunk calls the frontend directly instead of
      through checkpoint(), which is strictly less work, not a behaviour
      change (checkpoint() already no-ops functionally when grad is
      disabled; this makes it explicit rather than relying on that).
18.4  Second, smaller fix: the uint8 -> float / 255 conversion used to
      happen once for the WHOLE flattened batch, in VOStep._encode_visual,
      before encode_pairs ever saw it - about 2.1 GiB for a real 480-pair
      validation batch, on its own. Moved inside encode_pairs' per-chunk
      encode() closure, so at most one chunk's worth of pairs are ever live
      as float at once. encode_pairs' contract changed accordingly: it now
      takes raw image dtype (uint8) directly, not pre-normalised float - the
      call site in _encode_visual was updated to stop converting before the
      call, and a regression test
      (test_encode_pairs_converts_uint8_input_without_double_normalising)
      pins that a caller must NOT pre-divide by 255.
18.5  New tools/train_fixedwing_vo.py startup log line (guarded on not
      --disable-visual-input): reports the correlator's estimated peak
      candidate-tensor size in GiB at the CONFIGURED --frontend-chunk (or,
      if chunk is disabled, at the whole per-step pair count, loudly). This
      is the number that decides whether a run OOMs the moment validation -
      or a large --batch-size - is reached, so it is printed at startup
      rather than discovered from a crash.
18.6  New tests/test_encode_pairs.py - nothing exercised encode_pairs
      directly before this file. A fake counting frontend pins the exact
      regression (20 pairs, chunk 4, no_grad -> 5 calls of 4, not 1 of 20;
      same split with grad enabled; chunk=0 still means one call; a ragged
      remainder is not padded or dropped); a real (small) VisionMambaFlow
      Frontend confirms chunked and unchunked encoding produce identical
      tokens and quality under no_grad, so chunking is pinned as a memory
      optimisation only, never a numeric one; a pinned unit check of the new
      GiB estimate against the 480-pair/85 GiB and 8-pair/1.4 GiB numbers
      above. Reverting the fix (chunk<=0 or not grad-enabled, restored) was
      checked to fail the two no_grad chunking tests before landing it,
      same discipline as every other fix this session.
18.7  Validation's OWN correctness was re-audited on request and found
      already clean: evaluate() is correctly decorated @torch.no_grad() (an
      easy thing to misdiagnose by mis-reading an offset Read call, which

18.8  Host-RAM/`/dev/shm` pressure from `--num-workers` x world_size x

20. REVIEW OF THE TRAINER AND THE EVALUATOR (planar, --output-on-pairs, DDP)
-----------------------------------------------------------------------------
Both scripts were re-read end to end against the configuration actually
trained. The core is sound: the streamed evaluator feeds the model exactly
what training does and scores the same ticks (checked numerically, 6e-8);
the LR schedule, DDP metric reduction, early stopping, splits and baseline
are right. What was wrong, and is fixed:

20.1  Every DDP rank was seeded identically and never re-seeded, so all ten
      GPUs drew the SAME dropout masks, photometric jitter and loader-worker
      seeds: the extra ranks added no augmentation diversity. Ranks are now
      re-seeded with seed + rank after DDP has synchronised the weights.
      Checked with a real 2-rank run: rank 0 and 1 jitter now differ.
20.2  A non-finite prediction was silently DROPPED from the metrics, so a
      model that blew up on its hardest ticks scored better and could become
      best.pt. It now counts as an infinite error (an epoch with one is never
      selected). A non-finite LABEL still just removes its tick.
20.3  The evaluator's per-leg sums had the same hole the other way round:
      NaN * 0 is NaN, so one non-finite tick anywhere in a block - even an
      unscored one - turned vel_rmse into NaN and hid the block's maximum.
20.4  Checkpoints are written atomically (temp file + rename): a job killed
      mid-save no longer leaves a truncated last.pt that --resume cannot read.
20.5  A resume from an older checkpoint (epochs/epoch_0100.pt while best.pt
      is epoch 120) restored a worse "best" and the next epoch to beat it
      overwrote the better best.pt. The better of the two is now kept.
20.6  A resume silently kept the checkpoint's learning rate and weight decay
      when the command asked for different ones (a new --learning-rate, or
      --lr-scaling on a different GPU count) while logging the new value. The
      change is now applied, like a changed --epochs: rebuilt, fast-forwarded,
      and logged.
20.7  --velocity-loss simple never trains the variance and direction-
      confidence heads; they are now frozen. Nothing changes numerically, but
      newer PyTorch (2.14 here) crashed DDP at the start of epoch 2 with
      "Expected to have finished reduction in the prior iteration" because of
      them - the ORIGINAL code did too, in this environment. A server upgrade
      would have hit it.
20.8  Evaluator, max-error times: "t@max" and the plots' time axis were tick
      index x median interval, early by the whole length of any telemetry gap
      before them. Now read off the telemetry clock.
20.9  Evaluator, pre-split runs: with no --dataset it scored the run's TRAINING
      folder and labelled it held-out validation. It now defaults to the run's
      validation folder, and scoring the training folder is reported as NOT
      held out.
20.10 Stratification: turn_rate_deg_s is |yaw rate r|, which under-reads a
      steep turn (heading rate x cos bank) and is blind to a pull-up. Kept as
      it was, and rotation_rate_deg_s (|p, q, r|, all the rotation the frontend
      removes) added beside it.
20.11 --disable-visual-input with --output-on-pairs is refused in both tools:
      outputs exist only on delivered pairs, so it scored nothing (loss 0,
      NaN metrics, no best.pt) instead of giving a floor.
20.12 The evaluator's cold-start warm-up warning left out the extra wait for
      a non-overlapping tiling's first pair (130 ticks, not 85, here).
20.13 New startup NOTE when --max-visual-events is far above the pairs a window
      actually holds. With --output-on-pairs a 6 s window has ~12 pairs, so the
      default 120 pushes ~108 zero-padding slots per window through the
      frontend and the loaders: same result, several times the compute.
      commands.txt 3b now passes --max-visual-events 14.

NOT changed - decisions for the user:
20.14 With --output-on-pairs the scored ticks are the DELIVERED pairs, and
      delivery depends on learned quantities (fit weight vs --min-fit-cells,
      the speed cap). An epoch that refuses its hardest pairs scores better on
      fewer ticks. val_visual_kept_fraction was 1.0 throughout the planar run,
      so no effect yet - but read it next to val_vel_rmse once any reliability
      gate is turned on.
20.15 The automatic --warmup (135 ticks) masks the first ~2 of a window's ~12
      pair outputs, because a pair captured just before a window starts is
      delivered inside it. Kept: it is also the recurrent state's warm-up. A
      shorter --warmup buys ~15% more supervision if wanted.
20.16 DistributedSampler pads validation by repeating up to world_size - 1
      windows, so validation numbers shift slightly with the GPU count.
20.17 metrics.csv's fixed 6-decimal format prints a learning rate below 1e-6
      as 0.000000. The format is pinned by a test, so it was left alone.

20.18 Tests: tests/test_evaluation_fixes.py (5), tests/test_training_fixes.py

21. --pair-stride: A ONE-SECOND PAIR EVERY HALF SECOND
-------------------------------------------------------
21.1  With --output-on-pairs the time between outputs was forced to equal the
      pair length: 0.5 s pairs every 0.5 s. At 200 m a 0.5 s pair moves the
      ground only a little in the image, so matching error is large relative
      to the motion (untrained, rendered 200 m flight: 0.33 m/s per pair at
      0.5 s, 0.20 m/s at 1 s).
21.2  New --pair-stride FRAMES: how often a pair (and an output) starts,
      separate from --frame-gap (how long a pair is). --frame-gap 20
      --pair-stride 10 at 20 Hz is a 1 s pair every 0.5 s - pairs (0,20),
      (10,30), (20,40), ... - twice the ground motion per measurement at the
      EKF's 0.5 s output rate. Default: --pair-stride = --frame-gap, exactly as
      before, so existing commands, checkpoints and resumes are unchanged.
21.3  Everything downstream already handled stride != gap: the pair plan, the
      dataset, --random-pair-phase, the evaluator, the ONNX export and the
      standalone runtime. Only the trainer forced them equal. The resolved
      stride is in the checkpoint args and the resume fingerprint.
21.4  The automatic warm-up follows: latency + (gap + stride - 1) frames
      (185 ticks for 20/10, was 135 for 10/10). --max-frame-gap-s follows the
      pair length (1.5 s for 1 s pairs).
21.5  Costs, stated rather than hidden: each output averages the motion over
      1 s instead of 0.5 s, so it reacts more slowly to turns and speed
      changes; neighbouring outputs share an image, so their errors are partly
      shared (vo.var_scale in the EKF is there for that).
21.6  Refused without --output-on-pairs, or below 1 frame.
21.7  New tests/test_pair_stride.py (7 tests), including an ONNX export and a
      standalone-runtime replay of a rendered flight with 1 s pairs every
      0.5 s: delivery ticks identical to PyTorch, max velocity difference
      4.6e-5 m/s; and the evaluator against training on the same span with
      overlapping pairs: same pairs, same scored ticks, velocities equal. commands.txt 3c is the run to compare against the 0.5 s
      baseline.
